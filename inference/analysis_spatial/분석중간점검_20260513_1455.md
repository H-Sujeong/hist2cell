## 3. 분석 *방법* (통계·코드) 피드백

### 3.1 잘 한 부분 (계속 유지)

- **Permutation null** — CCA / Mantel / silhouette / axis intra-inter 의 4 종류 모두에 1000-perm null. 작은 N (=46–48) 에 대한 robust 한 통계 검정으로 가장 모범적.
- **PCA 10 dim 으로 자유도 제어** — CCA 입력 차원 (80, 4216~6148) 을 그대로 넣지 않은 것. trivial r=1 회피.
- **사전 등록 가설** — `proteomics_marker_hypotheses.csv` 에 가설을 *먼저* 정의하고 검정. post-hoc cherry-pick 방지. 8/8 의 강한 결과.
- **두 슬라이드 독립 재현성** — 코드 한 벌 (`_proof_ver2_lib.py`) 으로 동일 파이프라인을 두 슬라이드에 돌려 일관성 확인. CCA r 이 두 슬라이드에서 +0.94 로 거의 정확히 일치.

### 3.2 보완이 필요한 부분 (우선순위순)

#### (A) **PCA dim sensitivity sweep — 가장 시급**

`_proof_ver2_lib.py: N_PCS = 10` 이 hard-coded. PCA dim 이 바뀌면 CCA inflation 곡선이 *전체적으로 이동*한다 (dim 작아질수록 null 평균 ↓, observed 도 ↓). 보고된 +0.94 / +0.78 (null) 은 *dim 10 짜리 한 점* 의 결과일 뿐.

**권장.** dim ∈ {3, 5, 7, 10, 15} 그리드로 sweep 하여:
- observed CCA r vs PCA dim
- null 평균 vs PCA dim
- 두 값의 *차이 (signal)* vs PCA dim

이 곡선이 안정 평탄 (= 어떤 dim 이건 정성 결론 동일) 이면 dim 10 선택이 robust 함을 입증. dim 에 민감하다면 다른 dim 선택 정당화가 필요.
구현 비용 ~30 줄, 그림 1 장 추가. **`CCA_프레임워크.md` 의 dim=10 정당화 한 문장 만들기 위한 필수 sanity check**.

#### (B) **두 슬라이드 joint CCA — axis 부호 통일을 위해 필수**

현재 slide1 axis 1 + = "상피·선" / slide2 axis 1 + = "혈관·평활근". 같은 라벨인데 부호 반대. **이건 CCA 알고리즘의 임의성 (eigenvector 부호 불정)** 때문이지 *생물학적 차이* 가 아니지만, 두 슬라이드 결과를 직접 비교할 때 매번 "부호 뒤집고 보세요" 가 필요.

**권장.** 두 슬라이드 ROI 를 합쳐 (n=94) 한 번에 CCA 돌림.
- 양 슬라이드 공통 gene 만 사용 (∩(4216, 6148) ≈ 3500 정도 추정)
- 결과: axis 1/2/3 의 *통일된 부호* + section means 비교 표
- 슬라이드 간 axis 1 score 가 *비슷한 section 라벨끼리 같은 부호로 정렬* 되면 가장 강한 cross-slide 재현성 증거.

구현 비용 ~80 줄. 이게 되면 `summary.md` 의 슬라이드 비교 표가 *부호 정렬* 된 형태로 한 장에 들어갈 수 있어, 사용자가 "관련성을 모르겠다" 고 한 부분의 가장 큰 해소.

#### (C) **LOO per-ROI cosine — post-hoc bias 제거**

현재 `per_roi_cosine` 함수는 *같은 ROI 행렬*에서 marker 를 학습하고 *같은 ROI* 에 적용. 본인도 caveat 4번에 적어둔 약점.

**권장.** Leave-one-out:
- ROI i 를 빼고 나머지 N−1 ROI 에서 marker discovery → ROI i 의 proteomics score 계산 → ROI i 의 cosine
- N 번 반복하여 *unbiased* per-ROI cosine 분포

만약 LOO 평균이 현재 +0.555 / +0.559 와 비슷하면 post-hoc bias 없음의 직접 증거. 만약 크게 떨어지면 bias 가 컸다는 것 (즉 현재 결과를 보고할 때 LOO 값으로 대체).
구현 비용 ~30 줄. **사용자가 외부 보고할 때 reviewer 의 첫 질문 막을 분석**.

#### (D) **BH-FDR scope — 현 정의의 정직성**

`discovered_marker_pairs.csv` 의 BH 는 *800 개 후보* 위의 FDR. 80×G ≈ 337k–491k 전체 페어 위의 FDR 이 아님. 즉 *이미 top-5 로 추려진 pool* 안의 FDR.

본인도 caveat 2번에 적어둠. 단 **`top_discovered_pairs.png` 의 막대들이 "BH<0.05 통과" 로 표시되면 외부 reviewer 가 *전역 BH* 로 오해할 위험 크다**.

**권장 — 두 가지 중 하나**:
1. 그림 caption 에 *"per-cell-type top-5 풀 안의 BH-FDR. 전역 보정은 더 보수적임"* 명시.
2. *전역 보정* (80×G 전체) 도 같이 돌려 살아남는 pair 수를 보고. 코드 10 줄 추가만 하면 됨.

옵션 2 가 reviewer 견고. 옵션 1 은 최소 noise.

#### (E) **proteomics median imputation — sanity check**

`load_proteomics_matrix` 가 detection ≥50% 통과 gene 의 NaN 을 gene 별 median 으로 채움. 단일 modality 분석 (volcano) 에선 큰 문제 없지만, **PCA → CCA 의 PC1 이 *imputation pattern* 을 잡을 위험**. 특히 slide2 PC1 비중이 33.8% 로 크다는 점이 의심 신호.

**권장 — sanity check 만**.
- imputation 없이 (NaN 행은 PCA 에서 자동 drop) 다시 PCA → 첫 3 PC 의 explained variance 비교
- 두 결과가 비슷하면 imputation artifact 없음 입증
- 다르면 imputation 방법 (KNN-impute 등) 재검토

구현 비용 ~20 줄. **`summary.md` 의 "PCA 분산 22.6% / 33.8%" 라는 문장이 robust 하다는 증거가 된다**.

#### (F) **risk score pkl 활용** — 아직 분석에 들어가지 않은 결과

`git status` 에 `1_085_12_ROI_groups_risk_scores.pkl`, `1_152_19_ROI_groups_risk_scores.pkl` 가 untracked 로 있음. risk_gradient_figures.py 도. 이건 *결국 진짜 outcome* (각 ROI 의 risk score 연속값) 인데 현재 cross-modality 분석에 들어가지 않음.

**권장 — 가장 임팩트 큰 다음 단계**.
- ROI 별 CCA axis 1 score (H2C / Pro 평균) vs risk score 의 Pearson r
- 강한 양의 상관이면 **"axis 1 = 실제 risk gradient 의 두 modality 측정값"** 이라는 *생물학적 의미* 의 최종 증거
- section 라벨 (a/b/c/d/t) 대신 *연속 risk score* 를 쓰면 small-group 의 small-N 문제도 회피

구현 비용 ~50 줄. **본 점검 이후 가장 추천하는 다음 작업**.

### 3.3 코드 내 한 가지 잠재 버그 — 확인 권장

`_proof_ver2_lib.py:163-164` 에서 `PCA(n_components=n_pcs, random_state=seed)` 의 random_state 가 매 호출마다 같은 seed (=42). `permutation_null` 안에서 1000번 호출되어도 PCA seed 동일 → *결과는 입력 데이터 (perm) 가 다르므로 다르게 나옴*. 즉 *기능적으론 정상* 이지만, **PCA(random_state=…)** 는 SVD solver 의 sign flip 안정성을 위한 것이라 entropy 가 입력에서 와도 무방. **이건 버그가 아니라 인지만 해두면 됨**.

다만 `permutation_null` 안의 `rng = np.random.default_rng(seed)` 가 1줄 만들어지고 사용되지 않은 채 `rng.permutation` 만 호출되는 패턴. seed 가 1000 perm 전체에 1개라 *재현 가능* — 이건 *의도된 동작*.

→ **코드 자체엔 critical bug 없음.** sensitivity sweep (위 A) 만 추가하면 충분.
